# ASVS 5.0.0: область, доказательства и критерий выпуска

Цель — применимые требования ASVS 5.0.0 уровня L2; уровень L3 сохраняется в реестре для оценки риска. Полный каталог содержит 345 требований. Источник: [официальный релиз OWASP](https://github.com/OWASP/ASVS/tree/v5.0.0/5.0/docs_en). Файл `asvs_5_0_0_matrix.csv` содержит по одному уникальному требованию, уровень, решение о применимости, статус, владельца, доказательства и следующий шаг. `asvs_5_0_0_catalog.json` хранит ID/уровни и SHA-256 официального CSV для проверки происхождения. Названия разделов и идентификаторы происходят из OWASP ASVS, CC BY-SA 4.0. Старая матрица 4.0.3 сохранена как историческая; её числа не переносятся на 5.0.0.

## Что проверяется

Проверка Redis TLS clients описана в `redis_transport.md`: обязательная проверка
цепочки сертификатов и hostname, запрет URL overrides, настоящие TLS negative
tests. Это ограниченное доказательство V12.3.2; внутренний Redis остаётся
plaintext. ACL реализованы в `redis_isolation.md`; эксплуатационная проверка их
конфигурации и ротации остаётся открытой. Именованные роли не подтверждают
short-lived credentials по V13.2.1.

Контроль завершения критических worker/scraper задач и проверка их cleanup
описаны в `runtime_supervision.md`. Это ограниченное доказательство V16.5.3;
progress watchdog и эксплуатационная проверка восстановления остаются открытыми.

Область: Python Bot UI с long polling, scraper Pyrogram, worker, миграции, SQLite outbox, Redis Streams, PostgreSQL, сборка и CI. Grafana, Prometheus, Alertmanager, настройки хоста, Telegram provider, реальная БД, резервные копии и операционные процедуры требуют отдельного подтверждения. Готового стенда нет: эксплуатационные требования имеют UNTESTED или GAP, а не PASS. Факт отсутствия browser frontend, OAuth/OIDC, JWT, пользовательской загрузки файлов и WebRTC относится к приложению бота; browser security внешней Grafana от этого не становится подтверждённой.

Статусы: VERIFIED_DOCUMENTATION — документ описывает конкретное требование; PARTIAL — есть реализация/тесты, но требование целиком не подтверждено; GAP — известный пробел; UNTESTED — отсутствует достаточное доказательство; N/A — указана конкретная причина неприменимости. Эти статусы не означают сертификат OWASP. Проверка CSV в CI предотвращает пропуск ID и неподтверждённые заявления в реестре, но не тестирует сама все 345 требований. Ответственные роли Security maintainer и Operations owner должны быть назначены конкретным людям перед выпуском.

## Правила ввода и бизнес-процессов

Source payload: текст до 4096 символов; timestamp с часовым поясом, нормализация UTC, не более 300 секунд в будущем. Delivery payload: UTF-8 до 32768 байт, JSON object с уникальными ключами; неизвестные поля запрещены. Recipient ID — ненулевой целый в пределах 53 бит; canonical decimal string допускается для совместимости с Lua, float/bool/leading zero запрещены. Step — только целые 1/2/3; text — строка 1–4096; silent — bool. Event identity согласуется с source_chat_id/source_message_id/chat_id; source_message_id положительный. Location keys ограничены по длине и алфавиту, до 64 локаций. Generation — строка до 64. Старые jobs без source timestamp допускаются только как тихий исторический первый этап; повторные этапы для них отменяются. Invalid payload записывает только source ID и reason в DLQ, затем ACK; личное содержимое не сохраняется и не логируется.

Разрешения: пользователь определяется только по Telegram `from_user.id` из Bot API; callback не может указать владельца чужого профиля. Изменяемые поля — только документированные категории, локации, фразы и mute presets. Определение категории/локации — allowlist, длина custom phrase 3–30, максимум 5 custom phrases на пользователя и 5000 уникальных фраз глобально. DB запросы параметризованы. Удаление доступно в private chat; generation fence блокирует старые jobs после повторной регистрации. Полная независимая проверка всех callback и race сценариев ещё требуется.

Этапы доставки выполняются в порядке: 2 требует sent у 1, 3 требует sent у 2. failed/skipped завершают дальнейшие этапы. Clear после source ID отменяет релевантные повторы. Время проверяется снова после rate wait: >600 секунд означает тихий исторический первый этап или отменённый повтор; >7 суток отменяет любую доставку. Redis outage или потеря ownership не разрешает новую отправку. Stage lock и PEL heartbeat удерживают одну активную обработку и проверяют владельца перед send. Обрыв Telegram после принятия запроса остаётся неоднозначным: внешняя exactly-once доставка не заявляется.

## Соединения, ресурсы и секреты

Разрешённые внешние назначения: Telegram Bot API/MTProto, фиксированный api.ukrainealarm.com, административно заданные PostgreSQL и Redis. Пользователь не выбирает URL. Firewall egress allowlist пока GAP. UkraineAlarm HTTP timeout 8 секунд, connect 3 секунды; redirects запрещены. Redis worker/UI socket timeout 5 секунд, connect 3; consumer read block 1 секунда. PostgreSQL pool 10 + 20 overflow на процесс, connection 5 секунд и statement 10. Worker выполняет 15 delivery consumers; каждый резервирует один job. Ожидание rate slot 1–180 секунд, Bot API request 120; общий budget job 330 секунд при default settings. Lease TTL 90 секунд, heartbeat каждые 15, отдельный Redis guard timeout 5. Retry ошибок доставки — до 5 попыток, затем DLQ; source DB — до 6 неудач, затем DLQ. Для повторов действует общий лимит 5/s, все отправки — 20/s, отдельный chat — 1/s. Закрытие HTTP/Redis/DB ресурсов проверяется при shutdown; контроль завершения критических задач описан в runtime_supervision.md; отсутствие progress heartbeat всех сервисных циклов остаётся GAP.

Секреты: BOT_TOKEN, API_HASH, DATABASE_URL, REDIS_URL, UKRAINEALARM_API_KEY, Pyrogram session, Redis/Grafana credentials и Alertmanager credentials. Использовать secret files/vault injection, права только сервиса, отдельные runtime/migration roles; PostgreSQL-контракт и порядок включения реализованы в service_isolation.md, production-доступы ещё не подтверждены. PostgreSQL и Redis service roles разделены (service_isolation.md, redis_isolation.md); отсутствие vault/short-lived service credentials остаётся GAP. Проверять доступ ежемесячно; ротация штатно не реже 90 дней для service secrets, немедленно после компрометации или изменения доступа. Реальное исполнение ротации UNTESTED. Lock/generation tokens генерируются `secrets.token_hex(32)` (256 бит); UUID остаётся только для незащитных имён probes. HMAC-SHA256 псевдонимизирует ID в логах; используется отдельный обязательный LOG_PSEUDONYM_KEY из 64 hex-символов без fallback на API_HASH; порядок включения и ротации описан в secret_hardening.md. Реальная генерация, доступ и ротация ключа остаются UNTESTED.

## Инвентаризация логов и данных

Приложения пишут console и JSON rotated logs в `/data/logs/{service}.json.log`, максимум 20 MiB × 6 файлов на сервис; Docker stdout максимум 10 MiB × 3. В JSON: UTC timestamp, level, component, process/thread, message, exception и metadata. Configured secrets, credential URLs и Bot API tokens редактируются в обоих sinks; metadata с именем token/password/secret/authorization редактируется рекурсивно. Переносы строк экранируются против log injection. Сырые source/delivery payloads не должны записываться. Проверка известных secret literals не доказывает отсутствие всех возможных секретов: Pyrogram session из env/file теперь маскируется, но session database на диске и сторонние sinks нужно дополнительно проверить. Логи доступны только оператору, retention целевой 30 дней с ежедневным удалением и отдельным защищённым collector. Реальные ACL, централизованный collector, NTP и календарная retention — UNTESTED/GAP.

Классы данных: секреты/сессия — критические; user ID, subscriptions, mute, delivery jobs — конфиденциальные; агрегированные metrics без user labels — служебные. Не добавлять аналитику третьим сторонам с user profiles. Privacy delete очищает живые профили и per-recipient очереди, но AOF/backup/log copies требуют своей политики. Source/dedup horizon 30 дней, delivery freshness 600 секунд, delivery maximum age 7 суток, activity retention 30 дней. Политика backup: шифрование, ограниченный доступ, не более 30 дней хранения и документированное исключение удалённого профиля при restore. Исполнение backup policy ещё не проверено.

## Зависимости и выпуск

SBOM и pip-audit для каждого release; dependencies/actions/images из ожидаемых реестров, runtime hashes и SHA/digest pinning. Срок исправления подтверждённых рисков: активно эксплуатируемый/critical — 24 часа; high — 72 часа; medium — 14 дней; low — 30 дней. Еженедельный review обновлений. Рискованные компоненты: Pyrogram/MTProto session, tgCrypto native extension, сетевые clients, Redis Lua, migrator DDL и manual DLQ replay. Защита: отдельные непривилегированные контейнеры, ограниченные сети/секреты, staging перед обновлением, ручная проверка replay. Старый базовый image, dev hash lock, отдельные Redis/monitoring service roles и network policy требуют следующего пакета. Документирование SLA не является доказательством его соблюдения.

## Приёмка 9/10 и эксплуатационная проверка

1. Последовательно проверить и включить PR #9–#12 и это продолжение; заново проверить exact head и обязательный CI. Код только в открытых ветках не улучшает развёрнутую main.
2. Независимо проверить применимые L1/L2 требования. Каждый PARTIAL/GAP/UNTESTED должен получить воспроизводимый тест/доказательство или обоснованное решение N/A; blanket N/A по внешним провайдерам запрещён.
3. На изолированном стенде: 10 минут offline источника, restart/crash workers, Redis/DB outage, 429 и Telegram timeout, delete/re-register с активной очередью; подтвердить test alert реальным получателем.
4. Выполнить backup restore и проверить RPO <=60 секунд, RTO <=15 минут как целевые значения. Удалённые профили не должны возвращаться. Сохранить hardware, конфигурацию и журнал.
5. Утвердить аудиторию и нагрузку: первое уведомление P95 <=30 секунд, P99 <=60 секунд, отсутствие необъяснённых потерь. Для N адресатов и R постов/мин при трёх этапах необходимые условия стабильности: `3*N*R/60 <=20`, `2*N*R/60 <=5` (повторы). Даже без сети и 429 при R=20 это максимум N=7 для всех трёх этапов; это теоретическая граница, а не измеренная ёмкость. Синтетический Redis probe на 125 адресатов не доказывает такую доставку. Для большей аудитории необходимо продуктовое решение о coalescing/повторах и новое измерение.
6. Проверить real DB grants/RLS, Redis ACL, TLS внутренних соединений, secret rotation, logging ACL и alert routing. До этого общий 9/10 и полное соответствие ASVS L2 не заявляются.
