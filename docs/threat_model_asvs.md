# Модель загроз і стан ASVS 4.0.3

Джерело ідентифікаторів: [офіційний CSV OWASP ASVS 4.0.3](https://github.com/OWASP/ASVS/blob/v4.0.3_release/4.0/docs_en/OWASP%20Application%20Security%20Verification%20Standard%204.0.3-en.csv). [Матриця V1–V10](asvs_4_0_3_v1_v10_matrix.csv) містить усі 223 ідентифікатори цих розділів, рівні L1–L3, стан, доказ і залишковий ризик. `implemented_ci` означає тільки перевірку конкретної реалізації в CI, а не сертифікацію ASVS. `unverified` вимагає рішення про застосовність, тесту і власника контролю. Наразі 16 контролів мають конкретні докази, 207 залишаються непідтвердженими. Формальне твердження про відповідність ASVS або оцінку 9/10 до завершення цієї роботи є передчасним.

## Активи і межі довіри

| Межа | Можливість порушника | Захист у коді | Залишковий ризик |
|---|---|---|---|
| Telegram-канал → Pyrogram scraper | Скомпрометований адміністратор або хибний текст каналу | Фільтр конкретного `GROUP_ID`, outbox, явний source ID і час, відсікання відбою/заперечення | Джерело не має незалежного криптографічного підтвердження; NLP може помилятися |
| Telegram update → Bot UI | Підроблений callback payload, надмірні запити | Ідентичність з `from_user`, перевірка допустимих категорій/локацій, throttle, видалення тільки у приватному чаті | Потрібен незалежний RBAC/IDOR тест усіх callback-обробників |
| Scraper/Bot → Redis | Підміна або втрата подій, повторна доставка, виснаження пам'яті | Пароль локального Redis, bridge-мережа, зовнішній `rediss://`, атомарні Lua-операції, idempotency, DLQ | Немає окремих Redis ACL для сервісних ролей і перевіреного мережевого policy на продакшні |
| Worker/Bot/Migrator → PostgreSQL | SQL injection, читання локацій, небезпечна міграція | SQLAlchemy з параметрами, обмеження введення, TLS з перевіркою сертифіката, Alembic, RLS і відкликані Data API grants | Серверна роль має високі права; треба перевірити least privilege, Supabase network allowlist та відновлення бекапу |
| Код/CI → образи й пакети | Підміна залежності або release-артефакту | SHA для Actions, digest образів, lock із хешами, pip-audit та SBOM у CI | Потрібні регулярні оновлення, незалежний огляд SBOM та підписаний release |
| Метрики/логи/резервні копії | Витік токенів, ID, тексту загроз | Експортери без user ID у label; порт UI метрик не публікується напряму; агрегований MAU | Права хостових томів, строк backup/log retention і доступ операторів треба підтвердити на середовищі |

## Сценарії перевірки перед релізом

1. Ввести SQL-метасимволи у власну фразу й callback. Підтвердити, що зберігаються як дані, не змінюють структуру запиту і не відкривають чужі рядки.
2. Під'єднатися до PostgreSQL ролями `anon`/`authenticated`: `user_settings`, `user_triggers`, `user_activity_daily` та `alembic_version` не мають бути доступними через Data API. Окремо перевірити мережевий allowlist і права серверної ролі.
3. Створити загрозу, потім новіший відбій до другої стадії; друга і третя стадії не мають відправлятися. Перевірити текст джерела та час у першому повідомленні.
4. Видалити профіль з активною чергою, повторно зареєструватися і підтвердити, що старе покоління завдань не відправляється.
5. Вимкнути Redis, PostgreSQL, Telegram API та scraper по черзі; відстежити outbox, pending, DLQ, readiness, Alertmanager і реальне відновлення без пропусків.
6. Підмінити сертифікат PostgreSQL та спробувати зовнішній `redis://`: з'єднання має відмовити. Перевірити, що секрети не потрапляють у лог, образ або CI-артефакт.

Власник безпеки має позначити кожен рядок матриці як applicable / not applicable із обґрунтуванням, прикріпити тест або runtime-доказ та прийняти залишковий ризик. Поточна матриця навмисно не заповнює невідомі пункти припущеннями.
