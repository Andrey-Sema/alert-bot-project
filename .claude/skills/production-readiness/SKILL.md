# Production Readiness Checklist

Источник — дистиллированный список из ~130 инженерных концепций (resilience,
данные, деплой, безопасность, сеть, observability), которые обычно ломают
проекты после первого миллиона пользователей. Список не создан специально
под этот репозиторий — это внешний ориентир зрелости, а не ТЗ. Использовать
его нужно избирательно: не каждый пункт applicable к OdesaAlert Bot (Telegram
bot, докер-компоуз, Redis Streams + Supabase Postgres, без публичного HTTP
API и без multi-region требований). Форс-фитинг нерелевантных пунктов
(Kubernetes, WAF, saga pattern, multi-region failover и т.п. — для системы
такого масштаба) — это оверинжиниринг, а не production readiness.

## Как использовать этот скилл

**При написании кода** — не проходись по всему списку механически. Смотри,
какая категория касается конкретного изменения (новый внешний HTTP-вызов →
секция "Отказоустойчивость"; новая таблица → секция "Данные и хранилище";
новый env var → секция "Безопасность") и убедись, что релевантные пункты
соблюдены, прежде чем считать задачу законченной.

**При ревью / аудите production-readiness** — иди по категориям ниже
последовательно. Для каждого пункта:
- ✅ реализовано — сослаться на `file:line`, где это видно;
- ⚠️ частично / есть риск — описать конкретный сценарий отказа;
- ❌ отсутствует и применимо — конкретная находка с предложением фикса;
- N/A — не применимо на текущем масштабе/архитектуре, с одной фразой почему.

Не выдумывай проблемы, которых нет в коде. Не помечай как ❌ то, что для
масштаба этого проекта явно избыточно (см. пример N/A выше) — вместо этого
N/A с обоснованием.

## Протокол "release-ready" аудита

Когда пользователь просит подготовить проект к релизу по этому чек-листу
(а не просто ответить на вопрос), выполняй все четыре шага, не пропуская:

1. **Gap-анализ.** Пройтись по всем категориям ниже, зафиксировать находки
   (✅/⚠️/❌/N/A) с привязкой к файлам. Отдельно выделить, какие ❌/⚠️
   реально стоит чинить именно сейчас (соответствуют текущему масштабу и
   риск-профилю проекта), а какие — осознанно отложить (N/A с обоснованием).
   Не чинить ничего до согласования списка находок с пользователем, если
   объём правок нетривиален.
2. **Фикс.** Исправить только согласованные находки. Точечно, без побочного
   рефакторинга несвязанного кода — правило "no gratuitous changes" из
   основных инструкций репозитория действует и здесь.
3. **Ревью #1 (чистый код).** После фиксов — свежим взглядом перечитать
   именно изменённые файлы целиком (не диффом) в поисках хороших паттернов,
   которые стоит закрепить/задокументировать, и logical patterns, которые
   получились случайно и должны быть осознанными.
4. **Ревью #2 (антипаттерны, независимо от шага 3).** Отдельный проход —
   специально искать то, что фикс мог сломать или ухудшить: полумеры,
   рассинхрон между изменёнными местами и остальным кодом, новые race
   conditions/утечки ресурсов, забытые TODO, тихо проглоченные исключения,
   расширение blast radius правки за пределы согласованного скоупа. Это
   не повтор шага 3 другими словами — цель шага 3 закрепить хорошее, цель
   шага 4 — найти плохое, что появилось именно из-за фикса.

Итог — короткое summary: что исправлено, что осознанно оставлено как N/A
(и почему), что осталось как known risk с рекомендацией на будущее.

## 1. Отказоустойчивость и трафик (Resilience)

- **Rate Limiting** — на входящих обновлениях бота и на исходящих вызовах
  внешних API есть ограничение частоты (см. `throttling.py`).
- **Timeouts** — у каждого сетевого вызова (HTTP, БД, Redis) есть явный
  таймаут; нет вызовов, которые могут повиснуть навсегда.
- **Retries + Exponential Backoff** — временные сбои ретраятся с задержкой,
  а не мгновенным циклом; учитывается `retry_after`/`Retry-After`, если
  API его отдаёт (пример: `TelegramRetryAfter` в broadcaster).
- **Circuit Breakers** — при затяжном отказе внешней зависимости (БД,
  сторонний API) есть механизм "не долбить лежачий сервис", а не бесконечные
  ретраи, множащие нагрузку.
- **Идемпотентность** — повторная обработка одного и того же события
  (redelivery из очереди, повторный webhook) не должна давать дубли
  видимого эффекта для пользователя.
- **Очереди сообщений / Pub-Sub / событийная архитектура** — асинхронная
  передача между компонентами не теряет сообщения при рестарте потребителя.
- **Backpressure** — при переполнении внутренней очереди/буфера система
  либо равномерно замедляется, либо осознанно роняет данные — а не растит
  память безлимитно.
- **Dead Letter Queue** — сообщения, которые не удаётся обработать после
  N попыток, не пропадают молча и не блокируют очередь навсегда.
- **Распределённые транзакции / Saga** — применимо только если бизнес-
  операция реально затрагивает несколько независимых хранилищ атомарно.
- **API-шлюзы / реверс-прокси / балансировка нагрузки** — применимо, если
  у сервиса есть публичный HTTP-фасад перед несколькими инстансами.

## 2. Данные и хранилище

- **Пулы соединений** — есть connection pooling к БД с разумными лимитами
  (`pool_size`, `max_overflow`) и `pool_pre_ping`, а не соединение на запрос.
- **N+1 запросы** — при выборках связанных сущностей нет скрытого цикла
  запросов вместо одного JOIN/batch-запроса.
- **Индексация / оптимизация запросов** — частые/горячие запросы бьют по
  индексированным колонкам (проверить `EXPLAIN` для нетривиальных выборок).
- **Миграции БД / версионирование схем** — изменения схемы накатываются
  через миграционный механизм, а не ручными ALTER'ами; миграции идемпотентны
  и безопасны при повторном запуске.
- **Реплики для чтения / шардинг / партиционирование** — актуально при
  росте нагрузки на одну БД сверх возможностей вертикального масштабирования.
- **Репликация / выбор лидера / CAP-теорема / eventual consistency** —
  учитывать, если появляется несколько инстансов, пишущих в одно хранилище.
- **Оптимистичные / пессимистичные / распределённые блокировки** —
  конкурентные обновления одной записи не должны терять апдейты молча.
- **Race conditions / deadlocks** — конкурентный доступ к общим ресурсам
  (Redis-ключи, БД-строки, in-memory состояние) защищён от гонок.
- **Утечки памяти / сборка мусора / потокобезопасность** — долгоживущие
  asyncio-таски и фоновые воркеры не аккумулируют объекты без ограничений
  (см. паттерн `_background_tasks` в broadcaster: task добавляется в set и
  удаляется в `done_callback` — это правильный паттерн, не утечка).
- **Резервные копии / disaster recovery / failover** — для stateful-хранилищ
  (Redis с AOF, Postgres) есть понятная стратегия восстановления данных.

## 3. Деплой и операционная зрелость

- **CI/CD** — линт, тайпчек, security-скан и тесты гоняются в pipeline на
  каждый PR (см. `.github/workflows/ci.yaml`), а не только руками локально.
- **Docker / Kubernetes / Service Discovery** — образы воспроизводимы,
  сервисы не хардкодят адреса друг друга мимо DNS/service discovery сети.
- **Health checks / liveness & readiness пробы** — у каждого сервиса есть
  эндпоинт/команда, по которой оркестратор понимает "жив ли процесс" и
  "готов ли принимать трафик", и зависимости стартуют в правильном порядке.
- **Feature flags / Blue-Green / Canary / Rolling deployments / Rollbacks** —
  применимо, если релизы должны идти без даунтайма и с возможностью быстро
  откатиться; для одного докер-компоуз хоста может быть N/A с пометкой, как
  тогда делается откат на практике (`git revert` + redeploy — тоже валидный
  ответ, если это осознанный выбор, а не "не думали об этом").
- **Горизонтальное / вертикальное масштабирование / автомасштабирование** —
  если компонент должен когда-либо работать в нескольких репликах, он не
  должен полагаться на in-memory состояние или предполагать единственность
  инстанса без явной защиты (лок, лидер-электион) от дублирования эффекта.
- **CDN / кэширование на edge / инвалидация кэша** — применимо только при
  наличии публично раздаваемого статического/полустатического контента.
- **IaC (Terraform/Helm) / build caching / dependency hell** — инфраструктура
  и зависимости версионируются и воспроизводимы, а не настраиваются руками
  на сервере; конфликты версий зависимостей зафиксированы (lock-файлы).

## 4. Безопасность

- **Секреты** — секреты приходят из окружения/секрет-менеджера, не
  хардкожены в коде и не закоммичены; обязательные секреты падают при
  старте, если не заданы (fail-fast), а не тихо работают с пустым значением.
- **IAM / OAuth / ротация токенов** — доступ к внешним сервисам ограничен
  минимально необходимыми правами; долгоживущие токены имеют план ротации.
- **TLS / шифрование при передаче и на диске** — соединения к БД/внешним
  API идут по TLS, а не по plaintext.
- **CORS / CSRF / SQL-инъекции / XSS / SSRF** — применимо там, где есть
  HTTP-эндпоинты, принимающие пользовательский ввод; ORM/параметризованные
  запросы вместо конкатенации SQL — обязательно всегда, где есть SQL.
- **WAF / защита от DDoS** — применимо при наличии публичного HTTP-периметра
  под прямой нагрузкой из интернета.
- **Логирование PII** — персональные идентификаторы (chat_id, номера и т.п.)
  не должны попадать в логи/метрики в открытом виде без необходимости (см.
  `_hash_id`/HMAC-хеширование peer id в broadcaster — эталонный паттерн для
  этого проекта, держать его последовательным во всех местах логирования).

## 5. Сеть и протоколы

- **Таймауты и ретраи на уровне сети**, **расхождение часов (clock skew)**,
  **DNS**, **TCP vs UDP**, **HTTP/2 и HTTP/3**, **gRPC**, **webhooks** —
  учитывать в зависимости от того, какие протоколы реально использует
  сервис (здесь: HTTP к Telegram/Supabase/UkraineAlarm API, Redis-протокол).
- **Версионирование API / семантическое версионирование** — применимо, если
  у проекта есть API, которым пользуются внешние или разные внутренние
  клиенты одновременно с разными версиями.
- **Network partitions** — при временной недоступности Redis/БД сервис
  деградирует предсказуемо (например, не роняет процесс, не теряет тихо
  сообщения), а не падает в неопределённое состояние.

## 6. Наблюдаемость (Observability)

- **Логирование** — структурированное, с уровнями, без секретов/PII в
  открытом виде, единообразное между сервисами.
- **Метрики** — ключевые бизнес- и системные метрики (очередь, латентность
  доставки, ошибки внешних API) экспортируются и видны в Prometheus/Grafana.
- **Alerts / SLO / SLI / бюджеты ошибок** — алерты настроены на симптомы,
  влияющие на пользователя (не долетевшие вовремя алерты, просевший queue
  lag), а не только на "сервис упал"; если формальных SLO/SLI нет — это
  честный ⚠️ для сервиса, критичного по задержке доставки (ночные оповещения
  о тревоге), а не автоматически N/A.
- **Распределённая трассировка** — путь одного события через несколько
  сервисов (scraper → Redis → worker → broadcaster) можно проследить целиком
  по общему id/correlation-id, а не только по логам каждого сервиса отдельно.

## 7. Реальное время и доставка

- **Cron / WebSockets / Long Polling / Server-Sent Events** — способ доставки
  соответствует требованиям к задержке и нагрузке, а не выбран по умолчанию.
- **P99 latency / tail latency / throughput** — для критичного по времени
  пути (доставка ночного алерта) стоит понимать не только среднюю, а именно
  хвостовую задержку — она определяет реальный UX в худшем случае.

## 8. Эксплуатация инцидентов

- **Chaos Engineering** — намеренная проверка деградации при отказе
  зависимости (напр. Redis недоступен) — опционально, но полезно перед
  реальным релизом критичного по надёжности сервиса.
- **Инциденты в проде / on-call / postmortems** — есть понятный процесс
  "что делать, если ночью не долетели алерты" и разбор причин после факта,
  а не только мониторинг без процесса реагирования.
- **Cost optimization / cold starts / serverless limits** — применимо только
  при serverless/FaaS-развёртывании; для долгоживущих asyncio-воркеров N/A.
