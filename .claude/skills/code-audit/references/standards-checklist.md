# Чек-лист по стандартам

Загружается только когда `code-audit` доходит до фазы 2. Для каждого стандарта указано: что это, покрывается ли инструментами из фазы 1 или требует ручного рассуждения, и на что конкретно смотреть.

## OWASP Top 10 (веб-приложения)

**Покрытие:** частично semgrep (`p/owasp-top-ten`), остальное — ручной анализ.

Категории и на что смотреть в коде:

- **A01 Broken Access Control** — проверки прав на каждом эндпоинте/операции, а не только на уровне UI; IDOR (можно ли подменить ID в запросе и получить чужие данные)
- **A02 Cryptographic Failures** — hardcoded ключи/секреты, слабые алгоритмы (MD5/SHA1 для паролей), передача чувствительных данных без TLS, самодельное шифрование
- **A03 Injection** — SQL/NoSQL/command/LDAP injection: конкатенация строк в запросы вместо параметризации, `eval`/`exec` над пользовательским вводом, shell-команды с непроверенным вводом
- **A04 Insecure Design** — отсутствие rate limiting на чувствительных операциях, отсутствие бизнес-лимитов (например, неограниченное количество попыток/заказов)
- **A05 Security Misconfiguration** — debug-режим в проде, дефолтные креды, verbose error messages со stack trace наружу, лишние открытые порты/эндпоинты
- **A06 Vulnerable Components** — покрывается pip-audit/trivy, но также проверь: используются ли уже помеченные deprecated/unmaintained библиотеки
- **A07 Auth Failures** — слабая политика паролей, отсутствие лимита попыток входа, сессии без нормального истечения, JWT без проверки подписи/`exp`
- **A08 Software/Data Integrity Failures** — десериализация untrusted данных (pickle в Python — особенно актуально), CI/CD без проверки подписей пакетов
- **A09 Logging/Monitoring Failures** — чувствительные операции (auth, изменение прав, платежи) без логирования; логирование паролей/токенов в открытом виде
- **A10 SSRF** — исходящие запросы по URL, взятому из пользовательского ввода, без allowlist

## OWASP API Security Top 10

Применимо только если есть API-эндпоинты (REST/GraphQL/RPC/webhooks). Полностью ручной анализ — semgrep не покрывает специфику API.

- **API1 BOLA** — объектный ID из запроса используется без проверки, что он принадлежит текущему пользователю
- **API2 Broken Authentication** — эндпоинты без auth-мидлвари по недосмотру, слабая проверка токенов
- **API3 Broken Object Property Level Authorization** — mass assignment: весь объект из запроса пишется в БД без whitelist полей
- **API4 Unrestricted Resource Consumption** — нет лимитов на размер payload, пагинацию, глубину запроса (особенно GraphQL)
- **API5 Broken Function Level Authorization** — admin-эндпоинты доступны обычным пользователям при прямом вызове
- **API6 Unrestricted Access to Sensitive Business Flows** — нет защиты от автоматизации критичных операций (боты, скрейпинг)
- **API7 SSRF** — см. A10 выше, применительно к API-параметрам
- **API8 Security Misconfiguration** — CORS `*` с credentials, лишние HTTP-методы включены
- **API9 Improper Inventory Management** — старые/тестовые версии API остаются доступны в проде
- **API10 Unsafe Consumption of APIs** — доверие данным от сторонних API без валидации

## OWASP ASVS (Application Security Verification Standard)

Ручной анализ, привязан к уровню верификации:

- **L1** — базовая гигиена, применимо ко всему
- **L2** — для приложений с чувствительными данными (стандартный дефолт, если не указано иное)
- **L3** — критичная инфраструктура/высокие ставки

Смотри на: валидацию ввода на всех границах доверия, управление сессиями, контроль доступа, обработку ошибок без утечки внутренностей, хранение секретов (не в коде/конфиге в открытом виде).

## CWE Top 25

Не отдельная проверка — это система классификации. После находок из фаз 1–3 сопоставь каждую с CWE-ID, если он ещё не проставлен инструментом (semgrep обычно проставляет сам).

Наиболее частые в вебе/бэкенде: CWE-79 (XSS), CWE-89 (SQL injection), CWE-20 (improper input validation), CWE-200 (information exposure), CWE-352 (CSRF), CWE-434 (unrestricted upload), CWE-863 (incorrect authorization).

## NIST SSDF (SP 800-218)

Это про процесс разработки, не про конкретные строки кода. Ручной анализ на уровне репозитория:

- **PO (Prepare Organization)** — есть ли задокументированные требования безопасности для проекта
- **PS (Protect Software)** — зависимости закреплены (lock-файлы), секреты не в репозитории, доступ к репо ограничен
- **PW (Produce Well-Secured Software)** — код-ревью обязателен перед мержем, статический анализ в CI, тесты на security-кейсы
- **RV (Respond to Vulnerabilities)** — есть ли процесс/канал для сообщения об уязвимостях, обновляются ли зависимости регулярно

## SLSA (Supply-chain Levels for Software Artifacts)

Про целостность сборки, ручной анализ CI/CD-конфигурации:

- Зависимости закреплены по хешу, а не только по версии
- Сборка воспроизводима и изолирована (не на локальной машине разработчика)
- Генерируется provenance (метаданные о том, как и из чего собран артефакт)
- Артефакты подписаны

## CIS Benchmarks

Частично покрывается trivy/checkov для контейнеров и IaC, остальное — ручной анализ:

- **Docker:** non-root user в Dockerfile, минимальный базовый образ (distroless/alpine), нет `--privileged`, нет секретов в слоях образа
- **Хост/ОС** (если в скоупе аудита) — актуальные патчи, минимальный набор запущенных сервисов, файрвол настроен
